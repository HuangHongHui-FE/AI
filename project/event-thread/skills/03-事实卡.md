# 03 事实卡：把查证结果组织成结构化时间线

写 `facts/<slug>.json`。结构模板见 `facts/_template.json`。

## 顶层字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `slug` | ✓ | 英文短名，用于目录和文件名，如 `changan-xxx` |
| `name` | ✓ | 事件中文名，会成为文章标题主词 |
| `summary` | ✓ | 一句话说清是什么、起于何时、到何时。**不许用「近日」「最近」**（会被硬拦） |
| `started` | | 起始日期，支持 `YYYY-MM`（只查到月份时用，别补 `-01` 假装精确） |
| `ended` | | 结束日期；**留空 = 仍在发展中**。此字段只作记录，正文结尾由 `parts[].closing` 手写，不受它影响 |
| `parts` | | 分篇定义，见下方「分篇」——**长事件建议写** |
| `theme` | | 配色主题，默认 `cool`，可选 `ink`/`moss`/`warm`/`slate` 等 |
| `nodes` | ✓ | 时间节点数组，按时间升序 |

## 节点字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `date` | ✓ | `YYYY-MM` / `YYYY-MM-DD` / `YYYY-MM-DDTHH:mm` 三档精度 |
| `title` | ✓ | 这个节点发生了什么，一句话 |
| `level` | | `major` 重要 / `turning` 转折（**正文自动加粗**）/ `climax` 高潮 |
| `detail` | | 完整叙述段，说清来龙去脉 |
| `facts` | | **细节清单，密度主要靠这层**，每节点 2-4 条 |
| `images` | | 配图 `[{"src":"input/<目录>/xxx.jpg","alt":"图注"}]`，见 `04-配图.md` |
| `data` | | 数据卡片 `[{"value":"1.2亿元","label":"涉及金额"}]`，渲染成大字 |
| `quote` | | 引语 `{"text":"原话","speaker":"谁说的"}`，**必须注明说话人** |
| `confidence` | | `high`（默认）/ `low`（存疑） |
| `note` | | **`confidence: "low"` 时必填**，写明分歧或不确定之处。**这是内部批注，不渲染进正文**——存疑要靠 `detail` 的措辞体现，见 `05-发布.md`「内部批注不进正文」 |
| `sources` | ✓ | `[{"publisher","title","url","date"}]`，至少一条 |

### 日期精度：只写到你知道的那一档

**查不到具体日子就写 `YYYY-MM`，不要补 `-01` 或 `-30`。** 补出来的"精确"是编造的精度，跟「时间必须准确」直接冲突。

```json
"date": "2019-09"       ← 只查到月份，就这样写
"date": "2022-09-05"    ← 查到了日子
"date": "2026-06-21T10:00"  ← 精确到分钟（有明确发布时间）
```

排序时会自动把 `2019-09` 排在 `2019-09-30` 之前，不会错乱。

## 分篇：按叙事边界切，不按节点数均分

长事件（约 6000 字以上）建议分篇。用 `parts` 定义，**断点落在叙事转折处**：

```json
"parts": [
  {
    "title": "蔡磊确诊渐冻症：医生说他只剩三到五年",
    "summary": "2019年9月，41岁的京东集团副总裁蔡磊拿到一张诊断书：肌萎缩侧索硬化，也就是渐冻症。医生给的生存期是三到五年。他没有休养，而是把剩下的时间当成一次创业。",
    "closing": "一个被判了三到五年的人，把时间花在了给自己找不到答案、但别人可能用得上的地方。",
    "digest": "2019年9月确诊，医生说生存期三到五年。他辞去京东副总裁，建患者数据平台、发起冰桶挑战、宣布捐献遗体，又走进直播间卖货为药物研发筹钱。",
    "until": "2022-09-21"
  },
  {
    "title": "蔡磊捐了一个亿：渐冻症还没被攻克",
    "digest": "《相信》卖了200万册，他和妻子再捐1亿元。与此同时，一次感冒把他送进ICU，2025年他彻底失声——只剩眼球能动，靠眼控仪工作。",
    "until": "2025-12-30"
  }
]
```

- `title` —— 该篇的专属标题（比模板化的「XX全过程梳理」抓人）
- `summary` —— 该篇的**开头概述**。分篇时必须写，否则会拿全事件 summary，**上篇会剧透结局**（首篇只讲到 2022 年却写着「截至2026年已完全失声」）
- `closing` —— 该篇的**手写结尾**（总结/一句有分量的话/当事人原话）。不写就不出结尾，**不会退回模板套话**
- `digest` —— 该篇的专属摘要。**不写的话三篇会共用同一段总摘要**，读者在列表里分不清是哪篇
- `until` —— 该篇最后一个节点的日期（**含**），达到即切篇

不写 `parts` 时会退回按节点数均分，断点可能落在半句话上。

### 标题的两条硬规则

**① 序号统一前置，且只出现一次**

**用户 2026-09-30 定**：分篇序号一律放标题最前面，形式统一。

```
【上】蔡磊确诊渐冻症：医生说他只剩三到五年
【中】蔡磊捐了一个亿：渐冻症还没被攻克
【下】渐冻症新药上了《自然》：蔡磊却用不了
```

所以 **`parts[].title` 里不要再写「（上）」**——写了会被自动剥掉再统一加前缀，等于白写。直接写正文标题即可。

代码已处理：标题自带篇序（「（上）」「第2篇」等）会被剥离后统一加 `【上】` 前缀，不会出现两次。

**② 标题必须点名「主体 + 事件」**

**用户 2026-09-30 定**：标题要让读者在信息流里刷到就知道写的是谁、什么事。

反面（改前实测踩到）：

```
他41岁那年，医生说他还有三到五年      ← 「他」是谁？跟渐冻症什么关系？关联不上
他捐了一个亿，买不到自己的命           ← 同上
药做出来了，救的不是他                ← 同上
```

**规则**：
- 主体名（人名/机构名）必须出现
- 事件关键词（如「渐冻症」）必须出现——**三篇都要出现**，不能只靠首篇交代
- 忌用「他/她/它」指代主体，忌用「这件事/那场风波」指代事件
- 长度控制 20 字上下（含 `【上】` 前缀后仍要能完整显示）

**三篇的结构参考**：坠落与求生 → 高光与崩塌 → 转机与代价（蔡磊事件的实测方案）。

篇数与标题前缀由 `buildPartTitle()` 自动加（`【上】`/`【中】`/`【下】`），不用手写。

## 怎么写好一个节点

### 细节密度靠 `facts` 和 `detail` 分工

- `detail` 负责**讲清逻辑**：发生了什么、为什么重要、和前后的关系
- `facts` 负责**堆具体信息**：时间、数字、人名、地点、原话

反面例子（只有概述，没有细节）：

```json
{ "detail": "该事件引发广泛关注，各方反应强烈。" }
```

正面例子：

```json
{
  "detail": "通报发布后 3 小时内，相关话题登上微博热搜第一位，阅读量突破 4 亿。",
  "facts": [
    "通报发布时间为当日 21:47，由市公安局官方微博发布",
    "通报提到涉案金额 1.2 亿元，受害者 340 余人",
    "次日 9 时，当地成立专项工作组，组长为分管副市长"
  ]
}
```

### `facts` 列表只放「硬信息」，不凑数

**用户 2026-09-30 定**：每节点 2-4 条具体细节，但**信息量不足就别硬凑**。

从蔡磊事件的实采教训（三类典型错误）：

| 错误类型 | 反面例子 | 为什么不行 |
|---|---|---|
| **名词解释充数** | 「ALSFRS-R 是评估渐冻症功能的量表，满分48分…」 | 这是背景知识，不是**这个节点发生的事**。读者要看的是"那天发生了什么" |
| **跨时期信息混入** | 2022年首播节点里写「破冰驿站四周庆在 2026 年 9 月」 | 不属于本节点时间范围，读起来突兀 |
| **内部批注当事实** | 「录制时间：2024年8月（**未确认到具体日期**）」 | 括号里那句是写给自己看的，读者不需要知道我查得准不准 |
| **跨节点重复** | 「2024年科研总投入4000万元」在 2024-01 和 2025-01 各出现一次 | 同一数据出现两遍，显得注水 |

**判断标准**：这条信息能不能回答「**在这个时间点，发生了什么**／**当时的状况是什么**」？不能就别放。

数据重复的防法：写完通读一遍全卡，同一条数据只保留在**它首次发生的节点**。

### `level` 用在真正的时间线拐点上

不要每个节点都标 `turning`（会全部加粗，失去强调作用）。一篇里 `turning` 通常 1-3 个。

### `quote` 用一手原话

官方通报原文、当事人陈述、发布会答问——**不要转述**，转述会失真。没有可靠原话就不要放。

## 校验

```bash
node src/preflight.js facts/<slug>.json           # 只核查
node src/preflight.js facts/<slug>.json --render  # 核查 + 出 HTML 预览
node src/preflight.js --list                      # 所有事实卡状态
```

**硬拦项**（不过就发不了）：缺 sources / 来源缺 url / date 格式错 / date 是模糊词 / date 晚于今天 / 时间线乱序 / `confidence: "low"` 缺 note / summary 含模糊指代

**提醒项**（不拦）：单源节点过半 / 存疑节点占比高 / 标了进行中但最新节点超 30 天没更新

## 提交前检查清单

用户逐条提过的问题，**每次建卡后逐条自查**（都是实际踩过的）：

### 内容层面

- [ ] **无内部批注** —— `detail`/`facts` 里不出现「未确认到具体日期」「是两件事」「需要说明的是」「不宜当作」这类写给自己看的话
- [ ] **无名词解释充数** —— 列表里没有只作背景介绍、不描述当日事件的条目
- [ ] **无跨时期信息** —— 每条都落在本节点的时间范围内
- [ ] **无重复数据** —— 同一数字/事实只出现在它首次发生的节点
- [ ] **标题点名主体+事件** —— 不出现「他」「这件事」这类指代
- [ ] **每篇有专属 summary / closing / digest** —— 不许三篇共用同一段
- [ ] **结尾是手写的** —— 不是「以上为…事件仍在发展中」这类套话

### 格式层面

- [ ] **日期只到月** —— 卡片里显示 `YYYY-MM`
- [ ] **无导航语** —— 正文不出现「本文是第X篇」「时间跨度」
- [ ] **图片前后有空行** —— 否则不会被解析成 `<img>`
- [ ] **`:::time` 块内无 markdown 语法** —— 加粗用 `<strong>`，块内不写 `**`
- [ ] **配图与封面不同图** —— 同图会被自动去重，但最好一开始就选不同的

### 技术层面

- [ ] **来源齐全** —— 每节点至少 1 条，重要节点 2 条（虽不展示，但硬门会拦）
- [ ] **日期精度诚实** —— 只查到月就写 `YYYY-MM`，不补假的日
- [ ] **图片路径存在** —— 引用前 `ls` 核对
