# event-thread Skill 总览

事件全过程梳理 → 公众号草稿。把一件事从起因到最新进展按时间顺序理清，细节密、时间准。

## 触发词

- **「帮我梳理XX事件」「XX是怎么回事」** → 走 `01-选题.md`（用户指定分支）
- **「有什么值得梳理的事件」** → 走 `01-选题.md`（找选题分支）

## 流程

| 步骤 | 文件 | 做什么 |
|---|---|---|
| 01 | [01-选题.md](01-选题.md) | 定事件：用户指定，或扫四方向列候选等用户选 |
| 02 | [02-查证.md](02-查证.md) | 查事实：curl 抓国内源，每个时间点取证并交叉验证 |
| 03 | [03-事实卡.md](03-事实卡.md) | 建 `facts/<slug>.json`：把证据组织成结构化时间线 |
| 04 | [04-配图.md](04-配图.md) | 找图：下候选 → **停下等用户删图** → 定引用 |
| 05 | [05-发布.md](05-发布.md) | 过核查硬门 → 渲染 → 分篇推草稿 → 写日志 |

## 为什么是这个设计

**先有事实，后有文章。** 每个时间节点必须自带来源，正文由事实卡**确定性渲染**（不是 LLM 二次生成）——**发布内容 = 已核查内容**，中间没有环节能改掉一个日期。

这是为了满足「时间点必须非常准确」：不靠自觉，靠机器校验。

## 硬约束速查

- 节点无来源 = 不许发布（`src/preflight.js` 硬拦）
- **来源要写进事实卡，但不展示在正文里**（用户 2026-09-30 定）——校验照旧严格，只是不给读者看
- 时间不许写「近日」「最近」；查不到具体日子就写 `YYYY-MM`，**不要补 `-01` 假装精确**
- 媒体报道日 ≠ 事发日，以事发时间为准
- 口径冲突以官方为准，但必须在 `note` 写明分歧
- 配图下完候选要**停手等用户筛**，不许自己选完就发
- 长事件用 `parts` 按叙事边界分篇，**不按节点数均分**；序号嵌标题中段「XX（上）：副题」，且**每篇要有专属 digest**
- **标题必须点名「主体 + 事件」**，不许用「他」「这件事」指代——读者刷信息流要一眼知道写谁、什么事

## 边界

- **不追当天热点** —— 当天的事走 `wechat-img/skills/00-hotspot-publish.md`
- **不做预测/评论** —— 只梳理已发生的过程
- **不发未核查内容** —— 硬门不过就是不发，没有「先发了再补」

## 维护约定

**每次因用户反馈改了代码，同步更新对应 skill 文件**——否则流程会漂移，下次照旧文档执行就走不回新规矩。
